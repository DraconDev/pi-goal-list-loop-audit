# Goal/List Tool Surface, Queue + State Roots, Prompt Layers, Docs/Packaging — 2026-09-28

## Findings

### F1 [SEVERITY: MEDIUM] `complete_goal` newObjective ignores `updateGoal`'s failure and pre-bumps the in-memory goal revision, so a failed durable write still advances `revision` and reports success
- Where: `extensions/loops/goal-tools.ts:743` (`state.goal = bumpGoalRevision(state.goal);`) and `:748` (`updateGoal({...}, ctx);` — return value discarded); counterpart `extensions/loops/goal-orchestrator.ts:923-937` returns `false` and notifies when `writeGoalStateTransaction` fails; the correct pattern already exists at `extensions/loops/goal-tools.ts:3938-3950` (propose_task_list checks `const persisted = updateGoal(...)` and refuses).
- What breaks: `.pi-glla` becomes unwritable (read-only mount, full disk, permission change) and an agent calls `complete_goal` with `newObjective`. `updateGoal` writes no transaction, returns `false` before `state.goal = nextGoal`, and notifies "Goal update was not persisted". Execution nonetheless continues: line 763 ledgers `goal_tweaked` with the NEW objective, line 764 notifies "Objective updated (complete_goal newObjective): …", and the claim proceeds against the **old** objective. The revision was already bumped at line 743, and the settle writes of this same call (the comment at :741-742 says they keep the audited revision stable) then persist that phantom `revision+1` next to the *unchanged* objective. The revision-bound audit-validity gate (:768-773) compares the goal's current revision against the revision the last audit ran at, so a previously approved verdict is now permanently invalidated for a contract change that never happened on disk.
- Fix: capture the result (`const persistedObjective = updateGoal({...}, ctx)`), and on `false` return the same "not persisted, nothing changed" refusal propose_task_list already uses; move the `bumpGoalRevision` pre-step behind that success check (or drop it — `updateGoal`/`cmdTweak` own revision bumps).
- Confidence: high — the unchecked return, the pre-bump, and the notify/ledger lines were each re-read at the cited lines, and the failing branch is fully determined by `updateGoal`'s early `return false`.

### F2 [SEVERITY: LOW] `list_activate`'s schema types `n` as a number, so the dotted child label its own error message tells the agent to use is rejected before the handler runs
- Where: `extensions/loops/goal-tools.ts:3764` (`n: Type.Number({ description: "1-based position in the queue (1 = head)" })`) vs `:3781` (`"n must be a visible list position such as 1, 2, or 1.1 for a child item."`); the label grammar itself is `extensions/goal-loop-core.ts:3404-3412` (`parseVisibleListPosition` accepts `^\d+(?:\.\d+)?$` as a **string**).
- What breaks: an agent holding a queued subtask reads `1.1` out of `list_status` / `/list show`, and emits `{"n": "1.1"}` (models quote non-integer identifiers; a JSON number cannot carry a label token). Pi's schema validation rejects the call before `execute` runs, so the handler's own guidance text is unreachable in exactly the case it was written for and the agent retries blind. The tool description also never mentions the child-label form at all. (The repo's own history confirms schema validation precedes the handler: the fixed 500-char `leftOut` finding in the ledger was exactly this class — the schema refused what the handler meant to clip.)
- Fix: declare `n` as `Type.Union([Type.Number(), Type.String()])` and describe both forms ("integer 1-based top-level position, or a `1.1` child label"), keeping `visibleListPosition(queue, p.n)` unchanged.
- Confidence: high for the schema/handler disagreement (both re-read); medium on the exact host-side rejection message, which I did not execute against a live Pi host.
