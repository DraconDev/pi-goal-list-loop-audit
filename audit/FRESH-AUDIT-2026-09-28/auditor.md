## Findings

### F1 [SEVERITY: LOW] The worker labels EVERY `challenge:false` dispatch "skipped: light-tier audit", so the rework-streak skip is recorded with the wrong reason
- Where: `scripts/goal-auditor-worker.mjs:1104-1105` (`challengeState = "skipped: light-tier audit"`), `extensions/goal-loop-auditor-process.ts:1920` (`...(args.auditTier === "light" || reworkStreak >= AUDITOR_CHALLENGE_STREAK_LIMIT ? { challenge: false } : {})`)
- What breaks: the parent sends the same boolean for two distinct reasons — light tier, or `reworkStreak >= AUDITOR_CHALLENGE_STREAK_LIMIT` (2 comparable rework rounds, a FULL-tier dispatch). In the second case `result.challenge` is threaded verbatim onto the verdict (`goal-loop-auditor-process.ts:2052`) and stored in `auditHistory`/`/glla stats challenges` as `skipped: light-tier audit`. A full-tier audit that skipped the falsification pass because the goal was on its 3rd rework round is durably recorded as a light-tier audit, so a later convergence diagnosis reads the wrong cause.
- Fix: send the reason in the request (e.g. `challengeSkip: "light-tier" | "rework-streak"` alongside `challenge:false`) and have the worker format `skipped: ${request.challengeSkip}`; one-line default keeps old workers working.
- Confidence: high (both lines read directly; the parent sends one flag for two conditions and the worker hardcodes one label)

### F2 [SEVERITY: LOW] A job dir with a finished `result.json` but a still-alive *parent* lock is pinned `ambiguous` forever and is never reaped
- Where: `extensions/goal-loop-auditor-process.ts:1104-1112` (parent-lock branch: `live` if PID alive, else `dead`), and `extensions/goal-loop-auditor-process.ts:1170-1180` (`cleanupDeadAuditJobs` only reaps `status === "dead"`)
- What breaks: the parent writes the lock with `role:"parent"` before request/worker launch. If the host crashes after the worker wrote `result.json` but before it rewrote the lock with `role:"worker"`, the dir holds a finished result and a dead parent PID → correctly `dead` → reaped. The pinned case is the opposite: the parent PID number is later *reused* by an unrelated live process. `processAlive(pid)` is then true and the identity check fails, so the entry stays `ambiguous` ("PID is alive but worker identity does not match this job"). `cleanupDeadAuditJobs` skips ambiguous entries unconditionally, so the directory (with its full `request.json` prompt + `result.json` transcript) leaks past the 7-day retention ceiling forever. The no-lock+result escape hatch at line 1137 does not apply, because the lock file is present.
- Fix: in the parent-lock branch, if `auditDirHasResult(dir)` holds, classify `dead` regardless of parent liveness (a finished result proves the worker already exited; a live parent can only be reading it, never writing it).
- Confidence: medium (the code path and classification table are read directly; the trigger requires PID reuse plus a specific crash window, which I could not reproduce here)
