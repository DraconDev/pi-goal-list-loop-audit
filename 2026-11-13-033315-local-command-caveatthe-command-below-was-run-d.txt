● GLLA audit: why the final audit is slow, and what would improve the summary

  I measured this against your real history: 483 audit verdicts in
  .pi-glla/audits.jsonl, the tier decisions in the ledger, and the Nov 9–10
  session export. I didn't change any files.

  Audit timings so far: the median audit takes 4.1 min, but 1 in 10 takes over
  22 min. Audits that end in an error take a median of 25 min. The worst goal
  ran 16 h over 7 rounds.

  Part 1: The final audit (speed and "struggling to finish")

  1. The auditor re-runs gates that GLLA has already run. This is the biggest 
  problem.
  - Before the auditor starts, a mechanical pre-audit runs every command in the
    verification contract (for this repo that's npm run release:check, about 14
    min).
  - If those commands pass, their output is thrown away (goal-tools.ts:1443,
    goal-loop-shield.ts:1004). The auditor never sees it.
  - The auditor is then told to paste raw output for each contract item, so it
    runs the same gates again. Its tool budget is 5 min
    (DEFAULT_AUDITOR_TOOL_TIMEOUT_MS).
  - In the history, 282 of 483 reports re-run a full-suite command; 164 of them
    name release:check.
  - Most audit errors come from this:
    - three approvals were refused because bash was cancelled at 300 s;
    - one challenge round stalled the same way;
    - two pre-audit gates timed out.
  - Fix: have the pre-audit keep a receipt for each passing step (command, exit
    code, duration, revision, end of the output). Put those receipts into the
    auditor prompt, tell it not to re-run them and to spot-check narrowly
    instead, and let the regression shield accept a receipt as evidence for the
    matching contract item.

  2. On a first-time audit, nothing stops the challenge round from re-running 
  the full suite.
  - The "don't re-run the whole suite" rules (REWORK_SCOPE_RULES) only apply to
    rework rounds.
  - The challenge round (round 2) starts as a new process and is told to
    "re-verify the load-bearing claims", so on a first-time audit it runs
    everything again.
  - Fix: apply the same narrow-check rule to every challenge round. The receipts
    from #1 make this easy.

  3. The prompt asks for "one tool call at a time" (goal-loop-auditor.ts:208).
  - That line was added to stop the auditor's report from being cut off at the
    output limit. That's an output-size concern, but it also forces every read
    and grep to run one after another.
  - Fix: keep the chunking advice, but allow independent read-only calls to run
    in parallel.

  4. The cheaper single-round audit tier almost never happens.
  - Only 18 of 257 audits ran light; 239 ran full.
  - One trigger is the high-stakes keyword check, which fired 207 times. It also
    scans the verification contract, so npm run release:check matches release\b
    and forces a full audit for this repo on every claim.
  - The other trigger is the activity ceiling (more than 12 writes or 20 bash
    calls), which fired 209 times. Most real goals go over it.
  - Fix: scan only the objective, not the commands in the contract, and adjust
    the ceilings. This is a policy choice, so it's your call.

  5. The auditor's tool budget doesn't account for how long the gate actually 
  takes. If #1 lands, this mostly stops mattering. If not, set the budget from
  the measured pre-audit duration.

  Part 2: Waiting on dead providers

  6. A spent plan is retried as if it were a temporary rate limit.
  - MiniMax returned 429 … Token Plan usage limit reached: Upgrade your Token 
    Plan or purchase Credits.
  - In the Nov 10 session that error was retried 16 times over about 13 min.
    Then nothing happened for about 45 min until you switched model by hand.
  - The current tree still files it as rate-limit, which means waiting an hour
    on the same model; I checked this with a probe.
  - Two causes:
    - the billing pattern catches buy credits but not purchase credits or
      upgrade your plan;
    - the code deliberately treats any 429 as a rate limit, whatever the
      wording.
  - Suggestion: when a 429 says "upgrade" or "purchase credits", switch to the
    fallback model immediately. This reverses a documented rule, so I'd want
    your OK first.

  Part 3: The completion summary (compared with Claude Code, Codex and OpenCode)

  The card already has the right sections: headline, lede, changes,
  verification, follow-ups, next steps. What's left is mostly polish plus one
  real gap:

  7. The spacing is backwards (summary-renderer.ts). Each section is rendered
  separately, so there's a blank line under each heading but none between
  sections. Everything runs together; it's visible in
  audit/summary-captures/dark-120.ansi.

  8. Every change group is labelled "What changed · <area>". It repeats the
  "Summary" heading; the area name alone (in bold) reads better.

  9. There's no diff stat, and the "repository state" line says nothing useful.
  - Codex and OpenCode show "N files changed, +X −Y".
  - The card's repository-state line (buildFinalRepoStateLines) uses git status 
    --short. Your sync daemon commits within seconds, so in your repos it almost
    always says "Tree clean".
  - Fix: use git diff --stat from the revision the goal started at instead.

  10. Show where each piece of evidence came from. This is the one thing the
  other tools can't offer. With the receipts from #1, the verification table can
  say "GLLA ran release:check ✓ 14m02s" rather than a PASS read out of the
  executor's own notes, and mark items the auditor checked separately. So #1
  makes both the audit faster and the summary more trustworthy.

  11. Minor: pulling a path:line reference out of a sentence leaves the word
  before it dangling ("…an audit log for · extensions/…:1200").

  Suggested order

  1. #1 + #10 together: the gate receipts. This is the largest speed gain, it
     removes most audit errors, and it gives the summary real verification rows.
  2. #7, #8, #9: small, self-contained renderer changes that are easy to test.
  3. #2 and #3: prompt changes, cheap to make.
  4. #4 and #6: policy calls I'd like your answer on first.

  Should I start on #1 + #10, and which way do you want to go on #4 and #6?
